Beacon Hygiene: Surviving Modern EDR

In progress·Red team tradecraft
Working draft — drawn from CRTO study and engagement notes.

The old mental model of EDR evasion was signature evasion — change the bytes, defeat the hash, get past the scanner. That model is dead. Modern endpoint detection and response doesn't primarily care what your payload looks like on disk. It cares what your payload does, and it watches the places where doing anything interesting generates telemetry.

Defeating EDR is therefore not a signature problem. It's a telemetry problem. The question is not "will my binary get flagged" but "what signal does my activity emit, and can I reduce it below the threshold where it gets correlated into a detection." Once you frame it that way, beacon hygiene becomes the discipline of producing as little observable signal as possible.

Know What EDR Actually Sees

You cannot reduce a signal you don't understand. Modern EDR draws telemetry from a handful of well-defined sources:

  • Userland hooks — EDR injects into processes and hooks common API functions to observe calls before they reach the kernel. This is the layer that unhooking and direct syscalls aim to bypass.
  • Kernel callbacks — process creation, thread creation, image loads, and handle operations are reported to the EDR driver through documented kernel notification routines. These are harder to evade because they live below userland.
  • ETW — Event Tracing for Windows, particularly the .NET and AMSI providers, surfaces managed code execution and script content. This is why in-memory .NET tradecraft has to account for ETW patching.
  • AMSI — the Antimalware Scan Interface intercepts script and in-memory content for inspection at execution time.

Each source is a place you emit signal. The operator's job is to understand which of your actions hits which source, and to choose techniques that minimise the total.

Sleep Is When You're Most Exposed

A beacon spends most of its life sleeping between check-ins. During sleep, its memory sits in the process address space where memory-scanning EDR can find it — recognisable beacon structures, decrypted configuration, the artefacts of a known C2 framework. Sleep masking addresses this: encrypting the beacon's own memory during the sleep interval and decrypting only when active, so a scan during sleep finds noise rather than signal.

This is representative of the broader principle. The loud moments — injection, post-exploitation, lateral movement — get the attention, but the quiet moments are where naive tradecraft leaves recognisable artefacts sitting in memory for hours.

BOFs Over Fork-and-Run

The traditional post-exploitation pattern — fork a new process and run a tool in it — generates exactly the telemetry EDR is built to catch: process creation, thread creation in a remote process, image loads. Beacon Object Files run inline within the existing beacon process, performing their work without spawning anything, which removes an entire class of the most-watched telemetry events. The shift from fork-and-run to BOF-based tradecraft is one of the highest-leverage hygiene improvements available.

The reframe that matters: stop thinking about hiding the payload and start thinking about reducing the signal. Every action has a telemetry cost. Operate like you're being metered on it, because you are.
