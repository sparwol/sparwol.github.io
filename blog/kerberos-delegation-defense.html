Why Your Kerberos Delegation Configuration Is a Privilege Escalation Path

9 min read BloodHound · PowerShell · AD Hardening

I'm going to tell you something you probably don't want to hear: your Kerberos delegation configuration is almost certainly exploitable right now.

Not because you made a mistake. Not because you misconfigured something. But because delegation works exactly as designed, and the design assumes that compromising a service account doesn't matter. That assumption is wrong.

When we compromise a service account with delegation rights — and we will — we can impersonate users to other systems. Including privileged users. Including to domain controllers. This post walks through what attackers actually do with delegation, why your current controls don't stop it, and what you can do that actually works.

What Attackers See When They Look at Delegation

When we run BloodHound in your environment, one of the first things we look for is delegation. Three types:

  • Unconstrained delegation: The jackpot. Any user who authenticates to that system has their TGT cached in memory. We dump LSASS, grab the TGTs, and impersonate whoever we want.
  • Constrained delegation: Supposed to be restricted to specific services. But with S4U2Self and S4U2Proxy, we can impersonate any user without them ever authenticating. And the SPN restriction doesn't matter — we can request tickets for any service class on the target host.
  • Resource-based constrained delegation (RBCD): If we have write access to a computer object's msDS-AllowedToActOnBehalfOfOtherIdentity attribute, we can configure our own delegation. We create a backdoor on demand.

All three lead to privilege escalation. And all three exist in most domains we test.

Why This Is Worse Than You Think

Delegation abuse bypasses most of your security controls:

  • MFA doesn't help. We're not authenticating with passwords. We're using Kerberos tickets obtained through delegation. Your conditional access policies don't apply.
  • Privileged Access Workstations don't help. If your admin authenticates to a system with unconstrained delegation — even from a PAW — we get their TGT. Doesn't matter how hardened the workstation was.
  • Password complexity doesn't help. We don't crack passwords when we abuse delegation. We use the service account's existing Kerberos credentials to request tickets on behalf of users.
  • EDR doesn't help much. Rubeus and Impacket use legitimate Kerberos protocols. There's no malware signature to catch.
The only thing that stops delegation abuse is not having exploitable delegation configured in the first place.

How to Audit Your Current Delegation

First, you need to know what you have. Run BloodHound in your own environment. It's free, it's what attackers use, and it'll show you exactly what they'll see.

sharphound
SharpHound.exe -c All --zipfilename audit.zip

Load the output into BloodHound and run these queries:

cypher (bloodhound)
// Find unconstrained delegation (excluding DCs)
MATCH (c:Computer {unconstraineddelegation:true})
WHERE NOT c.name ENDS WITH 'DC01$'
RETURN c

// Find constrained delegation accounts
MATCH (u) WHERE u.allowedtodelegate IS NOT NULL
RETURN u
powershell (powerview)
Get-DomainComputer -Unconstrained | Select-Object name,dnshostname
Get-DomainUser -TrustedToAuth | Select-Object samaccountname,msds-allowedtodelegateto
Get-DomainComputer -TrustedToAuth | Select-Object name,msds-allowedtodelegateto

Whatever you find, write it down. You need to make decisions about each one.

What to Do About Unconstrained Delegation

Unconstrained delegation should basically never be enabled on anything except domain controllers.

For each system you find: figure out why it's there. Talk to whoever owns that system. Ask if they actually need delegation. Most of the time, they don't know it's enabled — it was checked during a deployment years ago and never reviewed. Test disabling it. If the application breaks, move to constrained delegation instead and configure it to only the specific services it actually needs.

For Citrix specifically: Citrix deployments love unconstrained delegation. You can usually migrate to constrained delegation with StoreFront and the XML service as targets. Test in dev first.

If you absolutely must keep unconstrained delegation, isolate that system in a separate VLAN, don't let privileged users access it, and monitor it heavily. Accept that if it gets compromised, you're probably losing the domain.

What to Do About Constrained Delegation

Check each account with constrained delegation for these two things:

Is protocol transition enabled? Look for TRUSTED_TO_AUTH_FOR_DELEGATION in the userAccountControl attribute. If it's set, attackers can impersonate any user without that user ever authenticating. If your app only uses Kerberos (not NTLM or forms-based auth), disable it.

Check the SPNs in the delegation list. If delegation includes a domain controller, understand that attackers can use /altservice to request LDAP tickets and DCSync your domain. Remove DC access if the app doesn't actually need it.

What to Do About RBCD

RBCD is about who can configure delegation in the future. The attack works when someone has write access to a computer object's msDS-AllowedToActOnBehalfOfOtherIdentity. BloodHound will show you this — look for accounts with GenericWrite, GenericAll, or WriteProperty on computer objects.

The most impactful fix: set ms-DS-MachineAccountQuota to 0. By default, any authenticated user can create up to 10 computer accounts. Attackers use this to create a machine account with an SPN, then configure RBCD with it.

powershell
# Check current value
Get-ADDomain | Select-Object -ExpandProperty DistinguishedName |
  Get-ADObject -Properties 'ms-DS-MachineAccountQuota'

# Set to 0 (test computer joins still work after this)
Set-ADDomain -Identity (Get-ADDomain) -Replace \
  @{"ms-DS-MachineAccountQuota"="0"}
Setting this to 0 may break deployment automation that relies on domain join via user credentials. Test first — but the security benefit is worth the operational adjustment.

Detection: What Actually Works

Detection for delegation abuse is hard. Most attacks use legitimate Kerberos protocols, so you can't block them. But there are signals worth monitoring:

  • Event 4769 — Kerberos service ticket requested. Look for S4U2Self or S4U2Proxy ticket options from unexpected sources. The event is noisy — thousands per minute — but patterns stand out.
  • Event 5136 — Directory service object modified. Alert on any changes to msDS-AllowedToActOnBehalfOfOtherIdentity. Any modification to this attribute on a computer object should be investigated immediately.
  • Event 4741 — Computer account created. If MachineAccountQuota is 0, any computer account creation from non-admin accounts is suspicious.
My recommendation: focus on prevention (removing unnecessary delegation) over detection. Detection is possible but requires significant tuning effort and baseline understanding.

Why Nobody Has Fixed This Yet

Delegation abuse has been publicly documented for years. The tools are free. The techniques are well-known. And almost no one has actually fixed their delegation configurations. Why?

  • Nobody knows what delegation they have. It was set up years ago by someone who's no longer with the company and never reviewed since.
  • Nobody wants to break applications. Disabling delegation might break something critical, and nobody wants to own that outage.
  • "Delegation" sounds like a normal AD feature, not a privilege escalation vector. Security teams don't prioritise it.
  • It's never caused a problem before — so it feels safe. Until we compromise that Citrix server and steal every cached TGT.

What to Actually Do Starting Monday

You don't need to fix everything at once.

  • Week 1: Run BloodHound. Identify what delegation you have. Export the list. This is your baseline.
  • Week 2: Unconstrained delegation review. For each system, determine if it needs unconstrained delegation. Test disabling it in dev. Move to constrained delegation where possible.
  • Week 3: Protocol transition review. Disable TRUSTED_TO_AUTH_FOR_DELEGATION unless the application specifically requires protocol transitions from non-Kerberos auth.
  • Week 4: Set MachineAccountQuota to 0. Test computer joins still work through your standard deployment processes.
  • Week 5: Set "Account is sensitive and cannot be delegated" on all domain admin accounts and high-privilege service accounts.
  • Ongoing: Alert on Event 5136 changes to msDS-AllowedToActOnBehalfOfOtherIdentity. Review delegation configurations quarterly.
The initial cleanup — removing unconstrained delegation, disabling protocol transition where it's not needed, setting MachineAccountQuota to 0 — closes the most common attack paths. It's not a one-time project, but this sprint gets you most of the way there.
